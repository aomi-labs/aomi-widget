---
title: Payments (x402 & MPP)
description: How payment methods, fallbacks, and wallet-backed transports work in the Aomi widget.
---

The Aomi backend resolves payments via a **default chain**:

```
Aomi credits  →  BYOK  →  MPP (Tempo)  →  x402 (Coinbase)
```

When a chat request is sent without an explicit `?payment_method=` (i.e. Auto), the backend walks this chain and uses the first method that succeeds. Aomi credits cover most chats; the chain only progresses when credits are exhausted. The widget's `<PaymentSelect>` lets users override the chain per-thread.

The widget itself ships **selection** out of the box. Wallet-backed methods (MPP, x402) require the host to install a payment-aware `fetch` backed by a connected browser wallet. Reference implementation: `apps/portal`.

## Selection-only (default)

Mount the widget normally. Auto requests succeed via credits/BYOK with no extra setup. Picking MPP or x402 in the composer will request the wallet-backed method, but without the dispatcher below the request will receive a 402 with no signer.

```tsx
import { AomiFrame } from "@aomi-labs/widget-lib";

<AomiFrame.Root>
  <AomiFrame.Composer withControl />
</AomiFrame.Root>;
```

## Wallet-backed (MPP + x402)

Three pieces. Each is opt-in.

The signing authority should come from the browser wallet layer you already use in the host app, typically wagmi or Para via wagmi-compatible clients. Do not ship raw private keys in frontend code or local verifier scripts.

### 1. Payment-aware `fetch` (the dispatcher)

The backend uses two **mutually exclusive** challenge formats:

| Method | Challenge header              | Success header     |
| ------ | ----------------------------- | ------------------ |
| x402   | `Payment-Required` (base64)   | `Payment-Response` |
| MPP    | `WWW-Authenticate: Payment`   | `Payment-Receipt`  |

Don't chain `wrapFetchWithPayment(mppFetch, ...)` — the inner wrapper rejects challenges from the *other* scheme (e.g. mppx throws `Missing WWW-Authenticate header.` on x402's `Payment-Required` 402). Instead, build a dispatcher that issues a plain `fetch` first and routes the retry by response header. In portal, both wrappers are built from the connected wagmi/Para wallet:

```ts
// see apps/portal/src/lib/payment-client-options.ts for the production version
async function paymentAwareFetch(input, init) {
  const probe = input instanceof Request ? input.clone() : input;
  const initial = await globalThis.fetch(probe, init);
  if (initial.status !== 402) return initial;

  if (initial.headers.get("payment-required") && x402Enabled) {
    return x402Fetch(input, init); // wrapFetchWithPayment(globalThis.fetch, ...)
  }
  if (initial.headers.get("www-authenticate") && mppEnabled) {
    return mppFetch(input, init); // Mppx.create(...).fetch
  }
  return initial;
}

<AomiFrame.Root clientOptions={{ fetch: paymentAwareFetch }}>...</AomiFrame.Root>;
```

There's also a small **request-narrowing** rule for the awkward case where MPP is disabled but x402 is enabled: append `?payment_method=coinbase` to Auto requests so the backend chain skips past the disabled tempo step. See `narrowAutoMethod` in `apps/portal/src/lib/payment-fetch-utils.ts`.

### 2. Status on the picker

`<PaymentSelect>` accepts an optional `getStatus(method)` prop returning `{ tone, label, connect? }`. The `connect` field stays in the shared API as a generic host-extensible capability. Portal's adapter intentionally omits it — wallet handshakes (MPP/x402) happen automatically on the first chat turn that reaches the wallet step, so there's no remediation action to surface for those methods. If you're integrating a different payment scheme that needs an explicit setup step, attach `connect` and the popover will render a CTA.

```tsx
import type { PaymentSelectProps } from "@aomi-labs/widget-lib";

const paymentSelectProps: PaymentSelectProps = {
  getStatus: (method) => {
    if (method === "tempo") return { tone: mppReady ? "ready" : "warning", label: mppStatusText };
    if (method === "coinbase") return { tone: x402Ready ? "ready" : "warning", label: x402StatusText };
    return undefined;
  },
};
```

Forward via `<AomiFrame.Composer controlBarProps={{ paymentSelectProps }}>`.

### 3. Settings panel (optional)

Install the `payment-settings` registry component:

```bash
npx shadcn@latest add https://aomi.dev/r/payment-settings.json
```

The panel is laid out around the chain: a hero "Aomi credits" card with a fallback-chain visualizer, two cards for the wallet fallbacks (MPP, x402), and a bundled BYOK section. Supply two props:

- `status` — same status object you'd use for `<PaymentSelect>`. Optional `credits` field renders a usage bar; otherwise the card just describes the model.
- `toggles` — `mppEnabled` / `x402Enabled` (and their setters); persistence is yours (e.g. localStorage).

Pass `providerKeys={false}` to hide the BYOK section if you don't have a `ControlContextProvider` upstream.

## Reference implementation

`apps/portal` shows the full pattern end-to-end:

- `src/lib/payment-fetch-utils.ts` — pure `narrowAutoMethod` helper (and unit tests).
- `src/lib/payment-client-options.ts` — `paymentAwareFetch` dispatcher + mppx/x402 wrapper construction.
- `src/lib/use-payment-status.ts` — overview poll + clear actions.
- `src/lib/use-payment-select-props.ts` — adapter from status to `<PaymentSelect>` props.
- `src/components/portal-aomi-frame.tsx` — wires all three into one `<AomiFrame.Root>`.
- `src/app/settings/page.tsx` + `src/components/settings/payment-settings.tsx` — settings route using the shared widget-lib panel.
