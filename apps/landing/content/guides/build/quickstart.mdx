# Quickstart

`AomiWidget` is the default consumer integration. It owns the chat frame,
credentialed Portal transport, account bridge, wallet providers, network
catalogs, and execution defaults.

## Install

```bash
npm install @aomi-labs/widget-lib
```

Import the precompiled stylesheet once in your application entrypoint. Package
consumers do not need Tailwind or an `@source` rule for widget internals.

## Choose an auth mode

### Para

```tsx
"use client";

import { AomiWidget } from "@aomi-labs/widget-lib";
import { paraAuth } from "@aomi-labs/widget-lib/providers/para";
import "@aomi-labs/widget-lib/styles.css";

export default function Assistant() {
  return (
    <AomiWidget
      apiUrl={process.env.NEXT_PUBLIC_AOMI_PORTAL_URL!}
      auth={paraAuth({
        apiKey: process.env.NEXT_PUBLIC_PARA_API_KEY,
        environment: "PROD",
        appName: "My app",
      })}
      height="640px"
    />
  );
}
```

### Privy

Keep the same widget and swap only the tree-shakeable auth helper:

```tsx
import { AomiWidget } from "@aomi-labs/widget-lib";
import { privyAuth } from "@aomi-labs/widget-lib/providers/privy";
import "@aomi-labs/widget-lib/styles.css";

export default function Assistant() {
  return (
    <AomiWidget
      apiUrl={process.env.NEXT_PUBLIC_AOMI_PORTAL_URL!}
      auth={privyAuth({
        appId: process.env.NEXT_PUBLIC_PRIVY_APP_ID,
        appName: "My app",
      })}
      height="640px"
    />
  );
}
```

### External wallet / SIWE

Omit `auth` when you do not want an embedded provider. External EVM wallets
can authenticate through Portal SIWE; chat remains available before a wallet
is connected.

```tsx
import { AomiWidget } from "@aomi-labs/widget-lib";
import "@aomi-labs/widget-lib/styles.css";

export default function Assistant() {
  return (
    <AomiWidget
      apiUrl={process.env.NEXT_PUBLIC_AOMI_PORTAL_URL!}
      height="640px"
    />
  );
}
```

Passing an empty Para key or Privy app id also resolves to providerless mode,
which makes optional local configuration safe.

## Configure the browser app

For Next.js:

```bash
NEXT_PUBLIC_AOMI_PORTAL_URL=https://chat.aomi.dev
NEXT_PUBLIC_PARA_API_KEY=your_para_publishable_key
NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID=your_reown_project_id
```

For Vite, use your normal `VITE_*` names and pass the values into `apiUrl` and
the auth helper. Para's browser SDK currently needs `buffer` and `os` browser
shims in Vite; the repository's minimal
[`apps/widget-consumer/vite.config.ts`](https://github.com/aomi-labs/aomi/blob/main/apps/widget-consumer/vite.config.ts)
shows the verified setup without injecting mutable Node globals.

`apiUrl` is the Portal/BFF origin, not the raw backend API. Portal owns
BetterAuth cookies, provider exchange, SIWE, canonical accounts, and backend
bearer minting. `AomiWidget` sends `credentials: "include"` for REST, polling,
and native SSE automatically.

## Register the consumer origin

Cross-origin consumers must be explicitly trusted by Portal:

```bash
# Portal server configuration; exact origins, comma separated, no paths
AOMI_TRUSTED_ORIGINS=https://app.aomi.dev,https://preview.aomi.dev
```

The browser-side provider identifier must match Portal's server-side verifier
configuration:

```bash
# Para on Portal
PARA_JWT_AUDIENCE=your_para_publishable_key
PARA_API_SECRET_KEY=your_server_only_para_secret

# Privy on Portal
PRIVY_APP_ID=your_privy_app_id
PRIVY_APP_SECRET=your_server_only_privy_secret
PRIVY_JWT_VERIFICATION_KEY=your_server_only_verification_key
PRIVY_IDENTITY_JWT_VERIFICATION_KEY=your_server_only_identity_key
```

Never put server verifier credentials in `NEXT_PUBLIC_*` or `VITE_*`
variables. Do not mount `/api/auth/*` or `/api/aomi/*` in the consumer; Portal
is the only auth/account host.

### Cookie deployment boundary

Cross-origin does not necessarily mean cross-site. The supported direct setup
keeps Portal and the consumer under one parent site, such as
`chat.example.com` and `app.example.com`. BetterAuth session cookies are
`SameSite=Lax` by default, and browsers—especially Safari—may block Portal as a
third party when the consumer uses an unrelated top-level domain.
[BetterAuth's cookie guide](https://better-auth.com/docs/concepts/cookies)
documents the same Safari/ITP boundary and recommends a reverse proxy or shared
parent domain.

For an unrelated domain, deploy Portal on a customer subdomain or configure an
infrastructure reverse proxy so the consumer calls a same-site `/api/*` origin,
then pass that origin to `AomiWidget.apiUrl`. The proxy may relay Portal routes;
it must not reimplement BetterAuth, provider verification, canonical accounts,
or AccountBearer minting.

## Run and verify

Start the app, open the widget, and verify:

1. Anonymous chat can create a thread.
2. The selected Para/Privy modal opens, or an external wallet can connect.
3. Sign-in makes `/api/aomi/account` return the canonical account.
4. Threads remain authenticated after refresh.
5. A wallet action reaches the local signing prompt without exposing a key.

## Source-owned shadcn alternative

Use the registry when you intentionally want copied source instead of the npm
package:

```bash
npx shadcn add https://aomi.dev/r/aomi-widget.json
```

The package is the smaller upgrade surface for most consumers. The copied
`AomiFrame` and wallet-kit components remain available for bespoke layouts.
